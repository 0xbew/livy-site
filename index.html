Write it down while it happens.

Livy records what your coding agents do: sessions, prompts, branch switches, the model behind each turn, token use, which instruction files actually loaded, and which version of each skill ran. One line per event, in an append-only ledger. It never blocks the agent.

Works with Claude Code and Amp, and reads Codex's own logs. Livy is one small Go program, built from source: the agents' hooks call it as things happen, a scheduled flush ships the ledger, and a background receiver takes the agents' OTEL export, as JSON or protobuf, unless you turn it off. Your data goes to a folder you choose, your own bucket, or a git repository.

The ledger

Facts that only exist at the moment they happen

After the fact you can recover the diff and the PR. You can't recover which model wrote a line, which rules file was in context, or how a session moved between branches. Livy writes those down as they happen.

Records Ids and facts

  • Session start and end, harness and version.
  • The model behind each turn, and tokens by type.
  • Branch switches, and PRs opened by an agent.
  • Prompts, with an id for each one.
  • Every commit, with the session and prompt behind it and its ticket key. Rebases and amends map old to new.
  • Tool approvals and refusals, per prompt.
  • Hook and tool names, and the size of the hook's input.
  • Which instruction files loaded, as repo-relative paths.
  • Each skill loaded: its name, a hash of its exact version, and whether the session or one of its subagents loaded it.
  • Which Livy build wrote each line.

Never Content

  • Reply text, unless you opt in on that machine.
  • Tool inputs or outputs, and shell commands.
  • Your working folder or transcript paths.
  • A skill's text, or the folder it came from.
  • A PR number read from gh pr create output.
  • Anything from repos outside the orgs you name.

Prompt capture is off by default. Until you turn it on for a machine, Livy stores only the prompt's id, not its text.

Agents

What it sees in each agent

Claude Code

Hooks call Livy at session start and end, on each prompt, each tool call and each skill load. Everything on this page applies.

Amp

A small plugin hands Livy each thread's start, prompts, tool calls, skill loads, PRs opened, turn ends and token use. It records threads on your laptop and, with a ready-made setup that ships through a git repository, in Amp's hosted machines. Those machines have no cloud credential, so they push to a git sink repository. livy drain copies what they pushed into your own sink, unchanged, and never overwrites an object that is already there. It refuses any object Livy's own emit could not have written, and the daily flush runs it when a drain source is set. Amp doesn't report which instruction files loaded, a model switch or a session end, so Livy says those are not observable instead of guessing.

Codex

Livy reads Codex's own session logs for token use per call and for prompts, and turns on Codex's OTEL export. Commits Codex makes get trailers. Codex doesn't call Livy's hooks yet, so its sessions, tool calls and skill loads are not recorded live.

Skills

Which skill ran, down to the version

Skills change, and a copy on one machine can drift from the copy on another. Each time Claude Code or Amp loads a skill, Livy writes a skill.loaded line: the skill's name, a hash of its SKILL.md and of its whole folder as they were on disk right after the load, and whether the model asked for it or a person typed /name.

When a subagent loads the skill, the line says which one. The line never holds the skill's text, the words typed after /name, or a path: a skill kept in a folder goes out as a hash of that folder.

{"event": "skill.loaded",
 "harness": "claude-code",
 "skill": "go-review",
 "scope": "project",
 "trigger": "agent",
 "subagent_type": "general-purpose",
 "sha256": "4c1e9a0b…",
 "tree_sha256": "b72d0517…",
 "hash_method": "disk-after-load",
 "recorder_build": "5d81c0e4a2f7"}
How it works

Four steps, all local

  1. 1Hooks

    Claude Code's hooks and Amp's plugin call Livy at session start, each prompt and each tool. Git calls it on branch switch and commit. Codex's logs are read after the fact.

  2. 2Ledger

    Each event becomes one JSON line, appended locally. A failed write is recorded as an error event, never dropped quietly.

  3. 3Emit

    At session end, at most every 5 minutes mid-session, and daily, the ledger is rotated, checked and compressed. Raw lines are never edited, and uploaded files stay on your machine for 30 days.

  4. 4Sink

    Segments go to a folder you choose, Google Cloud Storage, S3 or a git repository. Each file is named by its content, so a retry is harmless.

Commit trailers

Every agent commit, recorded

When Claude Code or Codex makes a commit, Livy adds the session, the harness and the model as git trailers. Your own commits get no trailers, but every commit in your repos is still recorded in the ledger.

The model is stamped only when one model did all of that session's work since its previous commit. If Livy can't be sure, it leaves the model out rather than guess. A trailer failure never blocks a commit.

livy why

What the agent did, behind any commit

When a deploy breaks, start from the commit. livy why <sha>, or a range like A..B, lists the sessions, prompts, tools, models and tokens behind that change, and the ticket it belongs to. It never prints prompt text.

livy profile

Where a commit's time went

livy profile <sha>, or a range, splits the time behind each commit into the agent working (model calls and tools), the agent waiting on you, and the rest. It prints each turn with its model calls, tools and subagents, the longest of them, and the rework it can see: fixup commits, amends and rebases, and files the session changed again.

It reads the OTEL spans Livy's receiver keeps on this machine. Where no span reaches Livy, for example when company-managed settings send Claude Code's OTEL elsewhere, it times a Claude Code session from Livy's own hooks instead and says so ("from hooks"); run livy install again to add the hook that times each tool call (without it, only shell commands are timed as tools). A session with model and tool calls but no prompt line, which happens when Claude Code was started in a folder outside the repo, is timed from its calls, and its turns are marked "turns inferred". It prints names, durations, counts and tool targets, never prompt text, an argument's value or a tool's output.

Each timed commit also carries its trace: a lane for the main agent and one for each subagent, named by its task label, and every model call with its tokens and a cache verdict: first call, hit, partial miss or full miss. A miss also gives its cause, such as a compaction, a switch of model or an idle gap past the cache's lifetime. A tool call shows its target: the file, folder, program, host or task label, never an argument's value or any output. Targets are scrubbed with your denylist (with none, no target is kept), stay on your machine for 90 days and are never shipped to your sink.

livy pr

A pull request's agent work, in one call

livy pr --json --repo OWNER/NAME --branch B gives the same answer as livy why and livy profile for all of a pull request's commits at once, plus the skills loaded while each commit was made, and an estimate of what the pull request cost. It writes one JSON document, so a PR viewer can show it beside the diff.

It reads only the lines those commits need from a local index Livy keeps as it records, so its cost follows the pull request, not the machine's history. livy reindex rebuilds the index, and the daily flush builds it when it is missing. With no usable index, it reads everything and says so.

The estimate prices each API call at the vendors' list prices, from a table built into the binary, which prices every Anthropic model the vendor lists as available or recently retired, each price with its source and the date it was read. A call to a model the table lacks, or with a prompt longer than any the vendor publishes a rate for, is counted as unpriced, never priced at $0 (OpenAI models, used by Codex, are not priced yet), so with any unpriced call the estimate is a floor. Beside it are the cache hit rate, the cache misses by cause, and the cache drops mid-burst: calls that lost the prompt cache within 5 minutes of the previous call and wrote it again. Your plan or contract may bill differently.

livy pr --json --repo acme/web --branch pay-412shortened
{
  "schema": "livy.pr/1",
  "commits": ["a91c0e2", "c7d3b10"],
  "source": {"kind": "index"},
  "why":     { sessions, prompts, tools, tokens },
  "profile": { agent, waiting, other, the trace },
  "skills":  [ each skill loaded, by version ],
  "cost":    { estimated_usd, unpriced_calls, cache_hit_rate, cache_misses, cache_drops_mid_burst }
}
livy incident

One file for the incident review

Give it the incident and the two deploys. livy incident INC-212 --range a1f03c2..d4e8b19 writes one Markdown pack: every commit in the deploy, which ones an agent made, the ticket each belongs to, and what the agent ran and spent to make it.

It holds ids and counts, never prompt text. Add --excerpts and it includes the prompts too, scrubbed the same way livy show scrubs them, and logs that they were revealed.

INC-212.md
# INC-212  checkout returns 500 after deploy

livy doctor

Check that Livy is still recording

If capture breaks, nothing errors. The ledger just goes quiet. livy doctor checks each piece in one command: the agent hooks and the Amp plugin, the ledger, the git hooks and commit trailers, where your data goes, the OTEL receiver and the daily flush. It exits 0 only when everything is recording, so you can run it from a script or CI.

On a machine with company-managed Claude Code settings, doctor works out which settings Claude Code actually uses, where managed settings override yours. It names each managed setting that keeps Claude Code's OTEL export from reaching Livy, and shows how many exports the receiver stored and refused. livy install leaves managed settings alone and prints the conflict. While Livy's own hooks time Claude Code, doctor shows those settings as ok with a note, not as a failure.

When Claude Code sessions were started in a folder outside the repo they worked in, doctor says so: Livy has their calls and tools but not their prompts, so their turns are inferred. Start Claude Code inside the repo to record prompts.

When a repo's git hooks have gone missing, doctor names the repo and prints the livy install line that puts them back. livy version says which build is installed, and every ledger line carries that build, so two machines can be compared.

Prompt capture

Prompt text stays on your machine

Livy keeps the text of your prompts in a private vault on your own machine for 90 days, so you can still see what was asked after the agent's transcripts are cleaned up. livy vault backfill fills it from transcripts already on disk.

livy show --prompt <id> or --commit <sha> shows you exactly what would be shared: secrets, credentials and the names on your denylist are replaced by scrub, Livy's public scrubber, and it refuses to run without a denylist. Since scrub v0.3.0 that includes password hashes and passwords with dots in them. Every reveal is logged with the prompt ids, never the text.

Sending prompt text anywhere is off until an engineer opts in on their own machine. It goes to its own destination, separate from the ledger, with a 180-day retention rule.

Install

Three steps on macOS or Linux

Needs Go 1.27 or later and git. Livy is open source under the Apache-2.0 license.

  1. 1 · Build
    Terminal
    git clone https://github.com/0xbew/livy && cd livy
go build -o livy ./cmd/livy
  2. 2 · Say what to watch
    livy/profile.json
    {
  "scope": {
    "orgs": ["your-org"]
  },
  "sink": {
    "type": "local",
    "path": "/Users/you/livy-data"
  }
}

    List the orgs whose repos Livy should record, and the folder the data goes to.

  3. 3 · Install and check
    Terminal
    ./livy install --config profile.json
livy doctor

Install adds hooks to Claude Code, a plugin to Amp when Amp is installed, OTEL export settings to Claude Code and Codex pointed at Livy's local receiver, a branch hook and commit hooks to each repo in your orgs, and a daily flush. Running it again changes nothing. livy uninstall removes exactly that and keeps your data. A data folder other than the one install set up, such as a scratch LIVY_DIR for a test, never uploads to the sinks in your own config, only to sinks named in that folder's config.json or set by the managed file or the environment; livy doctor says when one is in use.

Rules it keeps
Never block the agent

Every hook exits cleanly, whatever goes wrong. Your session and your commits never wait on Livy.

Never fail silently

When a real event can't be written, Livy writes an error event that says why. A damaged state file holds that pass and says so, rather than starting over and skipping or repeating data. A gap in the record is visible.

Raw is never rewritten

The ledger is append-only and the schema only grows. Anything built from it can be rebuilt from it.
